# abtest-platform

A self-hostable feature-flag and A/B-testing platform, built to show that experiment results can be trusted. A zero-dependency TypeScript SDK assigns users to variants locally with deterministic hashing and batches events to a FastAPI service backed by PostgreSQL. A Python worker attributes conversions and runs a statistics engine that guards against the classic mistakes: peeking (sequential testing with mSPRT), sample ratio mismatch, and bad attribution windows. A Monte Carlo simulator checks that those safeguards actually work. The full spec is in [docs/PRD.md](docs/PRD.md).

> **Status:** under construction. Done: M0 (scaffold: every service starts, but only `GET /health` does real work), M1 (the statistics engine in `server/src/abtest/stats`, not yet wired to any service), M2 (Monte Carlo validation of that engine: [docs/results/summary.md](docs/results/summary.md), regenerated by `make simulate`), M3 (the PostgreSQL schema in [db/migrations](db/migrations), applied automatically by `make dev` or by `make migrate`), M4 (deterministic assignment, the admin API for metrics, flags, experiments, and API keys, and the SDK config endpoint; interactive docs at http://localhost:8000/docs), M5 (the TypeScript SDK and the demo page at http://localhost:8080), M6 (event ingestion, `POST /v1/events`: duplicates counted, each invalid event rejected with a reason, exposures derived with server-side assignment checks, per-key rate limiting), M7 (the worker that attributes events and computes results snapshots every 5 minutes, the results API, and a traffic generator: `make traffic SCENARIO=checkout_button` or `SCENARIO=srm_bug` sends simulated users through the running stack), M8 (the dashboard at http://localhost:3000: pre-register an experiment, start it, and read its results), and M9 (performance: measured ingestion throughput, query plans, and load-test results in [docs/performance.md](docs/performance.md)). See the milestone list in the PRD (§22).

## Quickstart

Prerequisites: Docker with Compose (Docker Desktop, OrbStack, or Colima) and `make`.

```sh
git clone https://github.com/yengnongxiong/abtest-platform.git
cd abtest-platform
make dev
```

`make dev` creates `.env` from `.env.example` on first run, builds the images, and starts the stack. Source changes sync into the running containers (Docker Compose Watch).

| Service | URL |
|---|---|
| API health check | http://localhost:8000/health |
| Dashboard (password: `ADMIN_PASSWORD` in `.env`) | http://localhost:3000 |
| SDK demo page | http://localhost:8080 |
| PostgreSQL | `localhost:5432` (credentials in `.env`) |

## Dashboard

Sign in at http://localhost:3000 with `ADMIN_PASSWORD` from `.env`. The dashboard calls the admin API from its own server, so the server key never reaches the browser ([ADR-019](docs/decisions.md)).

- **Experiments:** each one's status, primary metric, users, days running, and a sample ratio mismatch (SRM) badge.
- **New experiment:** a pre-registration form: hypothesis, variants and weights, traffic, metrics with their expected baselines, the smallest lift worth detecting, alpha, and the analysis type. It shows a live sample-size estimate, and the days needed at your daily traffic.
- **An experiment:** start, stop (with a reason), clone, and "Update results now". Results per metric: a plain-language sentence, a verdict, a table, and the lift with its confidence interval over time. When the SRM check fails, a red banner hides the results until you choose to see them.
- **Metrics, Flags, API keys:** create and edit them. A new API key is shown once.

To watch a whole experiment happen, feed simulated users to one you started in the dashboard:

1. Create a conversion metric that counts `purchase` events.
2. Create an experiment with two variants named "Control" (the control) and "Big button", with that metric as the primary one, and start it.
3. Run `make traffic SCENARIO=checkout_button ARGS="--use-running --experiment-key <its key>"`. It checks that the experiment can take the scenario's users, sends 40,000 of them, and asks for fresh results.
4. Reload the experiment's page. `SCENARIO=srm_bug` loses 5% of one variant's exposures, and the SRM banner appears.

## SDK

`sdk-js/` is a TypeScript SDK with zero runtime dependencies, for browsers and Node 22+. It is **2,556 bytes min+gzip** (ESM build, measured by `cd sdk-js && npm run build && npm run size`). It isn't published to npm: build it with `npm run build` and use `sdk-js/dist/index.js` (ESM) or `dist/index.cjs`.

```ts
import { createClient } from "./sdk/index.js"; // sdk-js/dist/index.js

const client = createClient({ clientKey: "ck_...", apiBaseUrl: "https://api.example.com" });
await client.ready(); // never blocks longer than readyTimeoutMs (2 s by default)

if (client.getVariant("checkout-button") === "big-button") {
  // show the big button; the exposure is logged once per user per page session
}
if (client.isEnabled("dark-mode")) {
  // ...
}
client.track("purchase", { value: 49 });
```

Assignment happens in the browser with no network call; the SDK polls the config (with an ETag) every 30 s and sends events in batches, retrying safely. See [ADR-014](docs/decisions.md) for the delivery guarantees. In Node, call `client.close()` when done, so its timers stop.

## Development

Host-side tools: [uv](https://docs.astral.sh/uv/) and Node 24 (see `.nvmrc`).

| Command | What it does |
|---|---|
| `make setup` | Install Python and Node dependencies on your machine |
| `make test` | Start Postgres, then run the Python and SDK tests |
| `make lint` | ruff, mypy, ESLint, and TypeScript checks |
| `make simulate` | Run the Monte Carlo validation and regenerate `docs/results/` |
| `make migrate` | Apply database migrations and bootstrap the default project and API keys |
| `make traffic SCENARIO=checkout_button` | Send simulated users through the running stack (see `scenarios/`), then print the results. `ARGS="--use-running --experiment-key <key>"` feeds an experiment started in the dashboard |
| `make seed EVENTS=10000000` | Fill a separate database, `abtest_perf`, with that many simulated events for the performance measurements |
| `make perf` | Measure it: EXPLAIN of the attribution query, a worker look, the results read, and row-by-row vs batch inserts |
| `make loadtest` | Load-test the ingestion API with Locust, against `abtest_perf` |
| `make down` | Stop the stack |

Design decisions and their trade-offs are recorded in [docs/decisions.md](docs/decisions.md).
